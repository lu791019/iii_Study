# 學習內容通路經營手冊（Content Channel Playbook）

> 這份手冊說明 Dex 怎麼規劃一條「學習內容通路」：定位怎麼寫、內容怎麼分家、決策怎麼拍板、內容怎麼產製與上線、節奏怎麼排、成效怎麼看。
> 之後要開一個新的學習平台、社群或內容線，或要替現有平台加一塊內容時，照這份走。
>
> 「動機要浪漫、操作要直白。」——規劃文件裡的選詞原則

**來源**：Dex 的私人 repo `channel-learn`（cohort 教學平台的程式與內容）與 `channel-learn-planning`（規劃書、決策紀錄、grill 紀錄、盤點與 QA 清單），2026-09～10。
**先講清楚**：`channel-learn` 不是影音頻道，是一個 **cohort 教學平台**（題庫加瀏覽器內跑碼、真人批改、專題空間、作品集、職涯工具），搭配 Discord 社群，再從電子報、Threads、部落格導流進來。本文的「通路」指這一整套。標「推論」的段落不是 repo 原文，是我從結構歸納出來的。

---

## 做完這份，你會做到

1. 用一句對比句寫出內容通路的定位，再定好「北極星＋可量測 proxy」兩層成功定義。
2. 畫出內容分配表，每樣東西只有一個家。
3. 用 grill 質詢法加決策紀錄表，把模糊需求變成可實作的決定。
4. 照「單一來源 → 同步 → 實跑驗證 → 盤點 → 上線 QA」的流程產製內容。
5. 排出每天、每週、每月、每學期的內容節奏，並設計不會杜撰數字的成效檢視。

## 1. 定位

### 1.1 一句話定位：「不是 X，是 Y」

repo 原句的骨架是：**不是又一個轉職課，是一套帶你把作品從 0 拍到上映的製片體系。**

寫法拆解：

| 元素 | 寫什麼 | 範例的做法 |
| --- | --- | --- |
| 否定句 | 讀者已經看膩的同類（紅海） | 「又一個轉職課」 |
| 肯定句 | 你的方法論外殼，帶一個可想像的終點 | 「把作品從 0 拍到上映」 |
| 垂直 | 打穿市場的第一個領域 | AI／Data 工程轉職 |

### 1.2 使用者與使用節奏

- **主要使用者是成人轉職者**，有兩種節奏：在職夜學（碎片時間）和全職衝刺（長時間沉浸）。介面跟內容兩種都要撐得住：草稿暫存、複習線、斷點續接，還有能讓人專心很久的工作區。
- **第二使用者是教學者**（批改、帶專題、經營班級）。內容與機制要讓下一位老師也能拿去用。

### 1.3 成功定義分兩層

| 層 | 定義 | 為什麼 |
| --- | --- | --- |
| 北極星 | 學員轉職成功（拿到 Data／AI 職缺 offer） | 這才是學員真正要的 |
| 可量測 proxy | 完課率＋作品集完成率 | 北極星要很久才看得到，proxy 每期都能量 |

### 1.4 三層資產：行銷講上層，工程做下層

| 層 | 資產 | 能不能被抄 |
| --- | --- | --- |
| 產品 | 平台功能 | 會被抄（LMS 功能很擁擠） |
| 方法論 | 可命名、可傳授的帶專題框架 | 名字和詮釋權抄不走 |
| 垂直服務 | 講師的履歷、教材、真實學員案例 | 信任與戰績靠時間累積，抄不走 |

原則：**產品是載體，方法論是品牌核心，垂直是灘頭堡。**方法論文件公開當行銷資產，產品閉源。

### 1.5 敘事皮膚 vs 工程本體（紅線）

平台用「拍電影」當專題的敘事外殼（學員＝導演、專題被加工的東西＝主角、Demo Day＝首映），但規則很硬：

- **站內雙語並排**：電影詞旁邊永遠標著工程詞（「分鏡」旁邊寫「架構圖／資料流程圖」）。
- **對外產物一律用工程詞**：README、簡報、面試都一樣。不能讓學員學會一堆只有這個平台才懂的黑話。
- **隱喻有範圍**：電影詞只用在專題與作品集，題庫維持技能樹敘事，免得隱喻過載。
- **選詞也要過「圈外聽得懂」這關**：正規術語如果大眾聽不懂（例如「毛片」），就改用白話的詞（「每週放映會」）。

> 💡 可以直接借的觀念：**「主角＝專題把什麼東西從 A 帶到 B」**。在 DE 專題裡主角是資料，主角的成長線剛好就是 data lineage。這讓學員面試時講得出「我帶這批資料從一支爬蟲的 CSV 走到每天自動更新的雲端儀表板」。

## 2. 內容架構：每樣東西只有一個家

### 2.1 四條學習路徑，各有製作方式

| 路徑 | 內容來源 | 製作方式 |
| --- | --- | --- |
| ① 軟體基本功 | 講師既有課綱 | **自製涵蓋並重新配重**：每個單元標「直接重製／精簡帶過／加重」，前後端精簡到「看懂即可」，AI 協作、資料庫、雲端、資安加重 |
| ② DE 主線 | 課程手冊＋補充章＋分級題庫 | 教材 repo 是正本，**直接掛載**；題庫當練題種子 |
| ③ 專案實作 | 學生專題手冊、工作坊素材 | 收編進來，做成關卡地圖（每關都有檢核與作業） |
| ④ 職涯 Roadmap | 講師自己的職涯指南 | **模板化**：用同一套九區塊模板量產各職位指南 |

### 2.2 分配原則（2026-10 一次大整併時定的）

- **每樣東西只有一個家**：同一本手冊不能在兩張地圖各勾一次。要嘛合成一個出口，要嘛分工（一邊只管進度，一邊只管實作與內容）。
- **學員只需要記三件事**：看進度去哪、做事去哪、教材在哪。
- **入口頁（portal）只放進度與入口**，一個項目一張卡，內容不在入口頁展開。
- **能力記分板不算學習項目**：它是別處做完自動亮燈的地方，入口放在職涯區。
- 整併前先打 git tag、備份資料庫；要下架的內容**標成退場，不刪除**，這樣回滾只要重匯舊資料。

| 學員要做的事 | 唯一的家 |
| --- | --- |
| 看進度、找下一步 | 學習地圖（portal） |
| 讀教材 | 資料館 |
| 做題 | 題庫 |
| 跑示範專案 | 示範專案地圖 |
| 團隊專題 | 專題地圖 |
| 能力盤點 | 職涯區 |

### 2.3 平台＝帳本，社群＝現場

| 放哪 | 放什麼 |
| --- | --- |
| 站內（帳本） | 要沉澱、要連動資料、下一屆要能繼承的：題目 QA、專題空間、繳交與回饋、里程碑、週報、作品集 |
| Discord（現場） | 即時、揮發性高的：閒聊、即時求救、儀式貼文、活動通知 |
| 橋接 | 站內事件用 webhook 推到 Discord；Discord 訊息用深連結指回站內頁 |

一句話：**作品與知識沉澱在站內，即時的動態留在 Discord。**評價語彙（「認證新鮮」之類）只放在平台；Discord 裡讓學員自然用 👍👏，多教一個符號就多一份認知負擔。

### 2.4 專題生命週期（電影化五階段，摘要）

| 階段 | 專題對應 | 檢核產物 |
| --- | --- | --- |
| 開發期 | 選題、一頁 spec、成本估算、**JD 對照（預售）**、技術選型（試鏡紀錄）、pitch | 情境卡、選型表、JD 對照表 |
| 前製 | 架構圖與資料流程圖、設計評審、環境建置、分工 | 架構圖、角色卡、時程 |
| 拍攝期 | 演進七步（每步一個可跑的資料夾）、週報、mock data 先頂、feature freeze | 每步驗證通過 |
| 後製 | 重構、README、期中 demo、90 秒 demo 影片 | 乾淨的 repo、簡報 |
| 發行 | 合規自檢（robots／ToS／個資／secrets）、Demo Day、宣傳四件套（技術文、demo 影片、履歷更新、模擬面試）、復盤、**下一部** | 評分表、復盤、下一部企劃 |

缺口分析的結論值得記住：**製作的中段通常很紮實，缺口集中在「錢與觀眾」兩端**，也就是開工前沒想過給誰看、做完沒人知道。所以開發期要加 JD 對照，發行期要加宣傳和「下一部」，讓流程從一條線變成一個循環。

## 3. 決策方法

### 3.1 決策紀錄表

每個決定編號，寫上日期和拍板者，之後的文件都引用編號（「決策 #16」）：

| # | 決議 | 日期／拍板 |
| --- | --- | --- |
| 1 | …… | YYYY-MM-DD／講師 |

推翻舊決定時，**新增一筆「修訂 #N」**，舊紀錄不改，這樣看得出來是「知情翻盤」。

### 3.2 Grill 質詢法（把模糊需求問到能實作）

每個中型以上的功能或內容改版，都先開一份 `grill-<主題>.md`：

1. **質詢範圍與輸入**：讀了哪些檔、哪些程式。
2. **已查證（不用問的）**：先自己查清楚現況，例如「現在有兩套重疊的清單，同一支 API 回傳、內容卻不同」，不拿查得到的事情去問人。
3. **決策樹分支**：功能範圍／資料模型／值域與預設／權限與角色／舊資料相容／UI 行為／錯誤與邊界／多語系（不適用就標 N/A）。
4. **逐題紀錄**：`Q-01＝A：<決定>（拍板者／日期）`。每題給 A／B／C 選項，附「照建議」的預設。
5. **已拍板彙整**＋**未決清單**（分「已轉單」和「需雛型」）。

> 一個小提醒：拍板者說「中間先不用問我，做完再核對」時，就把待核對事項集中列成一張清單，做完一次交出去。

### 3.3 假設清單＋gate 制里程碑

- 規劃書開頭就寫：**全文除了標註的地方，都是假設，不是計畫。**
- 每個假設寫上「風險高低 → 驗證方式 → 門檻指標」，從風險最高的開始排。
- 里程碑採 gate 制：**過一關才開下一關的投入。**紀律是：首發驗證之前，不為遠景寫任何程式。
- Roadmap 每個 Phase 都標出它依賴的假設（例如「〔假設：學員會用線上練題取代紙本卷〕」）。

### 3.4 競品分析：結論寫成三份清單

不是為了選平台，而是拆解別人做得最好的機制，回頭優化自己的設計。結論固定分三份：**可採用／要改造／明確拒絕**。repo 裡的例子：

- 可採用：等級解鎖內容（用參與換內容）、期間榜讓新人也有機會上榜。
- 明確拒絕：只拿「被按讚」當貨幣（衡量的是受歡迎程度，不是學習成效，容易出現灌水文化）。

### 3.5 「先上、再 review」

文案先照語氣規範寫好上線，同時產出一張 **review 表（位置／上線文字／你的版本）**，講師直接在右欄寫新句子，之後一次套用。適合文案量大、講師時間零碎的時候用。

## 4. 產製流程

### 4.1 單一事實來源，平台只同步

- 教材 repo 是正本，平台的內容集合由同步腳本拉進來，檔頭註明「從 X 同步，別手改內文」，並保留 `source` 連結回原文。
- 同一份內容要放到兩個地方時，改用「延伸閱讀卡」互相連結，不要複製。

### 4.2 題庫產製（可自動判分的程式題）

```
寫題目定義 → 實際跑出 expected output → 在「跟平台同一版」的瀏覽器執行環境逐字比對 → 盤點表 → 匯入
```

- **驗證環境要跟正式環境一致**：平台在瀏覽器裡用 Pyodide 跑程式，驗證腳本就用同一版 Pyodide、照平台 worker 的邏輯跑。
- **出題避開平台做不到的事**（例如瀏覽器跑碼不支援 `input()`）。
- **盤點表**：tier × 題數 × 與目標的差距，並標明哪些在正式環境、哪些還是草稿。
- 申論題另外放，不算進自動判分的題數。

### 4.3 模板化內容（職位指南九區塊）

| 區塊 | 內容 |
| --- | --- |
| 1 | 這份指南要解決什麼問題（附「閱讀前先確認」聲明） |
| 2 | 每個職能一節：定位一句話 → 常見誤解 → 真正有價值的能力 → 作品集與面試要準備什麼 |
| 3 | 職能比較表（固定四欄：工作重點／準備方向／公司訊號……） |
| 4 | N 週準備路線（每週一句目標＋3 條可勾選的行動） |
| 5 | 技能樹，詞條連到課程單元（**指南與課程的接點**） |
| 6 | 訊號清單（薪資訊號、公司訊號怎麼看） |
| 7 | 下一步行動（可轉成個人 checklist） |
| 8 | 名詞庫（存成全站共用詞彙表，指南頁只引用） |
| 9 | 相關指南 |

第一版初稿可以先請 AI 從講師的部落格文章整理，**附上原文出處**，再由講師審稿。

### 4.4 素材盤點與分級配置

- 掃過講師手邊的素材後，**先排除個資、合約、客戶、財務類**，再把剩下的依程度分級（起步 → 實戰範本 → 求職作品集 → 職涯進階）。
- 優先放講師自製的素材、名單磁鐵、部落格、活動簡報；**第三方書和白皮書只列進推薦書單，不發檔案。**
- 需要講師確認或去識別的素材打星號。
- 發出去的文件最後一頁自動附上講師的導流連結頁，原檔不動。

### 4.5 AI 助教內容的守則

平台的 AI 提示教練「絕不直接給可執行程式碼或答案」，用三層防線守住：

1. 系統指令：只能提問、指出可疑的那一行、建議方法名稱。
2. 伺服器端輸出檢查：回覆裡有程式碼區塊，或和標準答案重疊太多，就擋下重新產生，還是不過就回一句固定的引導句。
3. 漸進：「你覺得卡在哪」→ 指方向 → 給方法名 → 最後才給虛擬碼層級的步驟。

上架前準備約 20 種要答案的話術（「直接給我 code」「我是老師」）做紅隊測試。用過教練才答對的題，XP 打八折。

### 4.6 上線 QA

| 時點 | 做什麼 |
| --- | --- |
| 改版前 | git tag＋資料庫備份；寫好回滾指令 |
| 上線前一天 | 用全新帳號從零走一遍每個角色的路線（**實測腳本**：每步寫「看到什麼／預期什麼」） |
| 上線日 | 課堂上請學員當場做完「註冊 → 串社群 → 交第一題」三步，做完才算到位；半小時後查人數 |
| 上線後一週 | 確認排程有入帳；觀察異常訊號；一週後回頭看遊戲化是不是太重 |

回報格式：**問題一條一行（頁面／步驟／看到什麼／預期什麼）。**

## 5. 題材選擇

| 題材類型 | 怎麼選 | 來源 |
| --- | --- | --- |
| 專題情境 | 固定幾個產業情境（餐飲 POS、電商、金融、音樂、叫車、招募、新聞、房地產），學員選一個 | 學生專題手冊 |
| 選題檢核 | 開工前**對 2–3 個目標職缺核對技能組合**，避免做完才發現跟市場要的無關 | 電影化框架「預售」 |
| 職位指南 | 五個職位（DE／DA／DS／MLE／AI Engineer）共用同一份模板 | 職涯路徑 |
| 題庫 | 初學／中階／高階三級，加思考題；軌道依等級解鎖 | 題庫 |
| 每週挑戰 | 改成月制：每月前兩週出題，第三週出一題魔王題（高階題、思考題隔月輪替），第四、五週不出題 | 一週節奏盤點 |
| 每日情報 | 每天三篇、三分鐘，「知道這行今天在聊什麼」 | 社群排程 |
| 公開頁（SEO） | 只公開**這個平台才有**的內容：職位指南、題目試閱、規則與新手路線 | 公開頁規劃 |

> ⚠️ 部落格文章**不要整篇複製到平台**，重複內容會互相稀釋搜尋表現。做法是平台放延伸閱讀卡連回部落格，部落格文章加「到平台練這題」連回平台。

## 6. 節奏

### 6.1 學期節奏（20 週制）

- **週次 × 複習對照表**：每週列主題、要複習的教材、對應題組、里程碑。平台首頁「本週該複習」卡就讀這張表。
- 題組發放：初學卷（第 2–4 週）→ 中階卷（第 5–7 週）→ 高階卷（第 8–10 週）→ 第 11 週起改推「錯題複習」，依批改結果動態指定。repo 原文註明這是預設值，待講師確認。
- 里程碑倒數：期初 D-7、期中 D-14、驗收 D-30／D-14／D-7。
- 推估不確定的週次，在表格裡標 ⚠️ 並列成「待校準清單」。

### 6.2 一週節奏

設計原則：**每天有固定的底色，再讓每一天都至少有一件「不是每天都有」的事。**

| 層 | 內容（摘要） |
| --- | --- |
| 每天 | 清晨收割前一天的社群活動；早上發通告與每日情報；晚上提醒閒置太久的人（可以關掉） |
| 週一 | 本週公告、出題 |
| 週中 | 隨堂小測、上週活躍度前三名專訪 |
| 週五 | 職缺週報 |
| 週日 | 給學員的每週回顧私訊；給講師的週報（最多人卡的題、意見箱 Top 3） |

節奏調整的經驗：

- 每日任務一開始是每天一張，後來改成**每人各自隨機隔 2–3 天**換一張，私訊只在出新任務的日子寄。
- 彩蛋從「每天」改成「每週隨機 3 天」，哪三天由「週次＋秘密值」雜湊決定，前一天猜不到。
- 想再加變化時，先列候選、**先不做，等開學看數據再說。**

### 6.3 年度題量

用「一週幾題 × 52 週」反推每個 tier 需要的題數（例：一週三題 → 每個 tier 至少 52 題，一年 156 題不重複），再用盤點表補缺口。

### 6.4 宣發時間軸（專題）

| 時點 | 儀式 | 落地 |
| --- | --- | --- |
| 立項 | 開鏡帖（前導海報＋一句 logline） | 社群貼文 |
| 開發期 | 3 分鐘 pitch（面試自我介紹的第一次排練） | 文件 |
| 功能凍結 | 殺青帖 | 社群貼文 |
| Demo 前一週 | 預告首發帖（90 秒 demo 影片＋正式海報） | 社群貼文 |
| Demo Day | 首映＋映後座談（QA 就是模擬面試的前菜） | 現場 |

三個儀式點都是**零開發**的，只靠社群貼文加流程。

## 7. 成效檢視

### 7.1 原則

- **還沒驗證之前，不在任何介面杜撰數字或見證。**沒有成效數據、沒有轉職案例，就明寫「尚無」。
- 每個假設都配一個門檻指標，例如「多少比例的學員會主動用框架語彙描述自己的專題」「模擬面試時，盲評分數有沒有可辨識的差距」。
- **XP 只獎勵真實的學習行為，不懲罰**：絕不獎勵「每日登入」本身，退件不扣分；黑帽機制（稀缺、好奇、損失）只做輕量調味。

### 7.2 要觀察的訊號

| 訊號 | 怎麼收 | 用來決定什麼 |
| --- | --- | --- |
| 每一步的完成時間 | 新手任務每步記 `done_at` 和來源（自動偵測／自己勾） | 算「幾天做完」，決定要不要加期限 |
| 即時偵測 vs 隔天收割備援的比例 | 社群步驟兩條路都記 | 偵測機制可不可靠 |
| 最多人卡的題 | AI 教練對話紀錄 | 每週給講師的週報、補教材 |
| 意見箱 Top 3 | 社群頻道 | 下一批要做什麼 |
| 綁定率、第一題提交數 | 上線日半小時後查 | 當場處理異常 |
| 試用期儀表板 | 一次性撈資料的快照頁，講師說「重撈」就重跑 | 試用期快速看整體 |

### 7.3 推論：怎麼套到其他內容線

（推論）把上面的做法套到電子報或社群內容線：先寫一句定位，定好北極星和 proxy（例如訂閱轉換、回訪率），每一期內容都標它在驗證哪個假設，三個月後回頭看曲線再決定要不要加碼。repo 裡把「build in public 連載能不能帶來合格流量」列為中風險假設，觀察期設三個月，但沒有寫出具體的量測結果。
