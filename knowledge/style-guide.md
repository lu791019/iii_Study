# 風格指南

整理自 Dex 的公開教材：DataDreamers 學員專題手冊、midterm-mvp-template、de-course、stock-crawler-de-course-materials、job-hunter-v2，以及本 repo 已產出的計畫書。每條規則的原文例句在 [style-evidence/](style-evidence/)。

## 核心心法

> 「業界專案不是把技術秀出來，是把情境、痛點、解法（最優解和最快解）、遇到的技術問題和如何處理等講清楚。」

- **對象是轉職者**：有動機、沒有業界經驗。先講痛點與為什麼，再講工具，最後用一句類比收束（「uv 就是 Python 版的 nvm + npm」）。
- **用面試官的眼光解釋每個要求**：每項作業都連到「面試官會看到什麼」「履歷上怎麼寫」，並給「面試 5 秒講法」。
- **把學員往 MVP 等級推**：

| 等級 | 樣貌 | 面試結果 |
| --- | --- | --- |
| 作業 | Notebook 跑得起，沒有架構圖，demo 只能手動 | 看不到亮點 |
| 作品 | 有敘述、能持續執行、技術棧豐富 | 跟其他人差不多 |
| MVP | 有架構圖、歷史紀錄、監控與下一步，能講為什麼選 A 不選 B | 面試官想深入了解 |

- **降低焦慮**：砍 scope、低分、做不完都說成正常且聰明（「砍 scope 不是失敗——是聰明」「完成到哪就 Demo 到哪」）。
- **誠實是評分標準**：反對「都很好」；估計值、實測版本、過期內容都要標明。

## 文件結構

1. **開頭一句話**：這份給誰、讀完能做到什麼；常用 blockquote 加一句心法。
2. **整條流程濃縮成一行箭頭**，在 README、速查卡、手冊、Notebook 反覆出現（`CSV → pandas → SQLite → LLM → FastAPI`）。
3. **「做完這一章，你會做到」**：4–6 條可驗證的動詞句。
4. **每步三件事**：目標 → 做法 → 產出；並寫 **✅ 完成標準**與**預期結果**（預期輸出原文貼出）。
5. **時間切到分鐘**，寫在標題上（「Step 2：ETL Pipeline（45 min）」）。
6. **「時間不夠？」最小路徑**：每個段落都給可跳過的部分。
7. **表格多於段落**：
   - 卡關處方：「卡關 → 處方」
   - 排錯：「你遇到的狀況 ／ 原因 ／ 怎麼解」（錯誤訊息照原文）
   - FAQ：「症狀 ／ 原因 ／ 解法」
   - 讀者路由：「你目前的狀態 → 必讀 → 下一步」
   - 速查：「手冊 ／ 內容 ／ 什麼時候看」
8. **❌ / ✅ 對照範例**：爛 vs 好的 commit、模糊 vs 具體的 persona、履歷寫法。
9. **每章結尾**：🎯 小作業 checkbox → 交付方式 → 💡 提示 → 「下一步 →」連結。
10. **想一想**：先讓學員想，再附完整答案，並處理常見誤解。
11. **計畫類文件**：檢核點、緩衝週、風險與對策表、「已定案的決策」與「不做的事」清單。

## 語氣

- 繁體中文、口語、短句；用「你」直接對學員說話，像教練不像老師，偶爾帶點幽默。
- 提醒用「一個小提醒」「建議習慣」，不用命令或責備。
- 業界術語不硬翻（sprint、scope、owner、PR、retro），第一次出現時括號補白話。
- 具體數字與時間預算（「Sprint Planning 限 45–60 分鐘」「打勾 ≥ 8 → 你準備好了」）。
- 短句格言、對比句（「在 whiteboard 上花 1 小時，省 10 小時打 code」）。
- 引導用提問，不直接給答案（「你現在在哪個資料夾？用 `os.getcwd()` 看看」）。

## 教學設計

- **固定骨架**：Data Pipeline 六階段、ML 六步驟（資料收集 → 清理與 EDA → 特徵工程 → 訓練 → 驗證 → 判讀），讓學員「再也不會不知道從哪開始」。
- **先跑通簡化版，再上正式版**；每章「只換一件事」。
- **故意製造失敗再修好**（append → 報錯 → upsert），區分暫時現象與真錯誤。
- **證明會動，不是看起來會動**：逐層驗證。
- **用無關情境示範語法**，再請學員「翻譯」到自己的資料。
- **外部依賴都有 fallback**，並明講「不影響完成度」；降級要明確印出，不靜默。
- **長期升級故事**：同一個專案從期中原型一路升級，「你的 GitHub repo 就是作品集」。
- **業界術語對照**：「raw、cleaned、analyzed 三張表，業界叫 Medallion Architecture」。
- **講師端最省力**：講師只看「卡關 ／ 風險」欄，有問題才介入；TA 守則是引導、不代打。
- **回饋固定句型**：肯定「你們的 ___ 做得很好」→ 建議「如果能再 ___」→ 連結下一步。
- **復盤**：每 sprint 末用 KPT ／ 4Ls，期末對照 Demo Day 評分表與履歷升級 checklist。

## 文件版本

- 同一主題常需兩版：**含程式版**（實作者）與**無程式版**（審核者、主管、非技術讀者）。
- 時程預設：短版 1–1.5 個月；完整版 2–2.5 個月，含一週緩衝。
- 舊文件開頭標「⚠️ 歷史文件」，並指向正式版本。

## 寫作紀律（避免 Dex 舊教材出現過的問題）

- **單一事實來源**：同一活動的檔名、時長、筆數、段數只定義一次，其他文件引用它。舊教材出現過：產出檔名 `report.md` 與 `pipeline_doc.md` 不一致、實作段數 2 段與 3 段不一致、「10 萬筆」與實際 2,000 筆不一致。
- 章節互相引用時核對編號與檔名，連結要能開。
- 實測後才寫進教材；記錄實測版本與最後更新日期。
- 給 AI 接手的文件開頭寫「For Claude：依照此文件逐 Task 實作」，並附接手摘要。
